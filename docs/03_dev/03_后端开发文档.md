## 一、技术栈与依赖

后端为 Python + FastAPI 单进程应用，SQLite 起步（预留 Postgres 升级路径，见 §四）。包管理统一使用 **uv**（禁止 pip 手写 `requirements.txt`），构建后端为 hatchling（wheel 只打包 `src/clew`）。

Python 版本要求：**`>=3.11`**（`pyproject.toml` `requires-python`；代码使用 `datetime.UTC`、`zip(..., strict=True)` 等 3.11 特性）。

运行时依赖（声明见 `prototype/backend/pyproject.toml`，锁定的解析版本来自 `prototype/backend/uv.lock`）：

| 依赖 | 声明版本 | 锁定版本 | 用途 |
|---|---|---|---|
| fastapi | >=0.115 | 0.161.1 | Web 框架：路由、依赖注入（RBAC 守卫）、pydantic 请求校验、multipart 上传 |
| uvicorn | >=0.30 | 0.54.0 | ASGI 服务器（开发用 `--reload`） |
| pydantic | >=2.7 | 2.14.1 | API 模型与导入记录结构校验 |
| pydantic-settings | >=2.2 | 2.16.1 | `.env` 配置加载（`Settings` 类） |
| python-multipart | >=0.0.9 | 0.0.32 | multipart 表单/文件上传（`POST /files`、`POST /import`） |
| openpyxl | >=3.1 | 3.1.5 | XLSX 解析：清单双 sheet、合并单元格/多级表头定位核查、回源预览 |
| pyjwt | >=2.8 | 2.15.1 | JWT 签发/校验（HS256）。**未使用 python-jose** |
| jsonpath-ng | >=1.6 | 1.12.0 | JSON 定位器 `json_path` 的解析与命中检查 |

开发依赖（`[dependency-groups] dev`）：`pytest>=8`（锁定 9.1.1）、`httpx>=0.27`（锁定 0.28.1，供 `fastapi.testclient` 使用）。

**刻意不引入**（以代码为准）：

- 密码哈希用 Python 标准库 `hashlib.pbkdf2_hmac`（SHA-256、随机 16 字节盐、240,000 次迭代），**无 passlib / bcrypt 依赖**（见 §五）；
- LLM 调用用标准库 `urllib.request` 直连 OpenAI 兼容 `/chat/completions`，**无 openai SDK 依赖**（见 §八）；
- 字段检索用 SQLite `LIKE`，**未引入 FTS5**（数据模型 §3.2 记录的 M4 取舍）。

## 二、架构分层与模块职责

分层结构：**`routes/`（HTTP 编排：参数解析、权限守卫、异常→HTTP 状态码）→ 服务模块（`import_service` / `lineage` / `preview` / `versioning` / `changes` / `security` / `ai/*` 等业务逻辑）→ `db`（SQLite 连接与 DDL）**。服务模块之间可复用（如 `ai/tools.py` 复用 `lineage.py` 与 `preview.py`；`seed_demo.py` 复用 `routes/files.store_upload` + `run_import` 正式路径）。单进程、单存储、无消息队列、无搜索集群（设计方案 §八）。

- **`.env` 位于仓库根**，不入库（`.gitignore`），模板见仓库根 `.env.example`（含 `SECRET_KEY` / `JWT_EXPIRE_HOURS` / `DATA_DIR` / `ADMIN_USERNAME` / `ADMIN_PASSWORD` / `CORS_ORIGINS` / `LLM_*`）。定位实现（`config.py`）：`ENV_FILE = Path(__file__).resolve().parents[4] / ".env"`——`config.py` 位于 `prototype/backend/src/lineagelite/`，向上 4 层即仓库根（`lineagelite → src → backend → prototype → ai-lineage`）。

## 四、数据库

### 4.1 建库流程与连接方式

- **首次启动**：`main.py` `lifespan` → `db.init_db()` 执行 `executescript(DDL)`（全部 `CREATE TABLE/INDEX IF NOT EXISTS`，幂等）→ 检查 `user` 表为空则创建初始管理员（`ADMIN_USERNAME` / `ADMIN_PASSWORD`，`display_name='初始管理员'`，`role='admin'`），并向 stderr 打印提示。
- **连接**（`db.py` `connect()`）：`sqlite3.connect(path, check_same_thread=False)`，`row_factory = sqlite3.Row`，`PRAGMA foreign_keys = ON`（edge 复合外键等约束实际生效），父目录自动 `mkdir`。
- **事务**：`get_db()` 是 `@contextmanager`——正常返回 `commit`，任何异常 `rollback` 并抛出，用完关闭。所有写路径（路由/服务）都在同一个 `with get_db()` 内完成，保证部分失败不落库。

### 4.2 schema 与数据模型 §二的对应

`db.py` 的 `DDL` 与数据模型 §二逐表对齐：`user`、`source_file`、`dataset`、`field`、`edge`、`import_batch`、`version_tag`、`annotation`、`change_log`、`rollback_record`（M3 新增，共 10 张表）。

实现补充（数据模型已记录，非漂移）：

- `import_batch` 增加 `rolled_back_at` / `rolled_back_by` 回滚留痕列（数据模型 §2.6）；
- `edge` 的同对唯一不变量由 **两个部分唯一索引** 兜底（`uq_edge_field` / `uq_edge_table`）——SQLite 的 `UNIQUE` 对含 NULL 组合按 `NULLS DISTINCT` 语义处理，表级边拦不住（数据模型 §2.5）；
- 索引：`idx_edge_to/idx_edge_from`（递归 CTE 主路径）、`idx_field_sf`、`idx_log_entity`、`idx_log_batch`、`idx_annot_target`、`idx_rollback_tag`，与数据模型 §六一致；
- 时间列统一存 ISO8601 UTC 文本（`changes.now()` 秒精度）。

派生视图：数据模型 §3.1 的 `v_dataset_edge` 视图**未在 DDL 中创建**——表级投影由查询按需推导（`_dataset_closure` 沿全部边遍历），不落库。

### 4.3 预留 Postgres

以设计方案为准：SQLite 起步、SQL 全部写兼容子集 + 递归 CTE（`lineage.py` 注释明确「仅用两种数据库都支持的标准 CTE 语法」）。迁移注意点见数据模型 §七：`AUTOINCREMENT`→`GENERATED ALWAYS AS IDENTITY`、时间列 TEXT→`timestamptz`、字段检索 `LIKE`→`tsvector`+GIN；递归 CTE 与复合 FK 语义一致无需改动。当前未引入任何 ORM / 迁移工具，DDL 即 `db.py` 中的静态脚本。

### 4.4 data_dir 目录结构

```
{DATA_DIR}/
├── lineage.db                      # SQLite（所有业务表）
└── files/<sha256前2位>/<sha256>.<ext>   # 托管源文件，按内容寻址
```

- `source_file.storage_path` 存相对路径（如 `files/ab/ab12….csv`），**不对外暴露**，访问走受控 API（`GET /files/{id}/download`、回源预览）。
- 文件名保留原始扩展名：openpyxl 等解析器按扩展名识别格式（`routes/files.py` 注释）。

## 五、认证与 RBAC

实现于 `security.py`（+ `routes/auth.py`），对应设计方案 §4.4。

### 5.1 JWT 与密码哈希

- **签发**：`create_token(username, role)` 生成 HS256 JWT，payload `{sub, role, iat, exp}`，`exp = iat + JWT_EXPIRE_HOURS`；密钥 `SECRET_KEY`。
- **校验**：`_bearer_payload` 要求 `Authorization: Bearer <token>`，解析失败/过期抛 401；`current_user` 提取 `{username, role}`。
- **密码哈希**：标准库 PBKDF2-HMAC-SHA256，随机 16 字节盐，`PBKDF2_ITERATIONS = 240_000`；存储格式 `pbkdf2$<迭代数>$<盐hex>$<摘要hex>`；校验用 `hmac.compare_digest` 恒时比较。永不明文存密码。

### 5.2 角色守卫（`require_role`）

`ROLE_ORDER = {viewer: 0, editor: 1, admin: 2}`；`require_role(minimum)` 返回 FastAPI 依赖函数：先过 `current_user`（401），**再实时查数据库中该用户的当前角色**（用户不存在 401；角色不足 403「需要 xx 及以上角色」）。角色以数据库当前值为准（JWT 中的 role 仅登录时签发），管理员改角色后旧 token 立即按新角色生效（测试 `test_r4_role_change_takes_effect_immediately`）。

### 5.3 各角色权限（以路由声明为准）

| 角色 | 允许的操作 |
|---|---|
| `viewer` | 全部读：登录/`me`、`GET /datasets`、`GET /lineage/subgraph`、字段回源预览、`GET /annotations`、`GET /changes`、`GET /version-tags` 与 diff、`GET /import/batches`、`GET /files` 列表与下载、`GET /ai/status`、`POST /ai/chat` |
| `editor` | viewer + `POST /files` 上传、`POST /import` 导入、`POST /annotations`、`PATCH /fields/...`、`POST/PATCH/DELETE /edges`、`POST /version-tags`、`POST /ai/suggest(/confirm|/reject)` |
| `admin` | editor + `POST/GET /users` 用户管理、`POST /import/batches/{id}/rollback` 按批次回滚、`POST /version-tags/{name}/rollback` 按标签回滚 |

（设计方案 §4.4 还规划 admin 可「删除数据集、重置导入」，原型未实现该端点，见 §十二。）

### 5.4 初始管理员

两条路径均兜底：`main.py` lifespan（首次启动 user 表为空时）与 `seed_demo._ensure_admin()`（演示数据需要合法 actor 满足 `source_file.uploaded_by` 外键）。登录后可由 admin 经 `POST /users` 建其他账号（角色三选一）。

## 六、导入流水线

对应设计方案 §三（导入格式规范，§3.5 校验规则 / §3.6 源文件托管）与数据模型 §四（JSON 结构）。整体链路：

```
① POST /files 上传源文件（sha256 去重）
        ↓
② POST /import 上传清单（manifest.py 三格式归一化）
        ↓
③ 行级校验 + 定位器结构校验（models.py pydantic）
        ↓
④ 实文件核查（locator.py CHECKERS，物化 resolved）
        ↓
⑤ 批次落库（import_service.run_import：fields → edges → change_log）
        ↓
⑥ 导入报告（import_batch.report JSON）
        ↓ （闭环）
⑦ 回源预览（preview.field_preview：定位卡高亮 + verification 留痕）
```

### 6.1 源文件上传（sha256 去重）

`routes/files.py` `store_upload(filename, data, username)`：

- 扩展名白名单 `csv/xlsx/json`（其余 400）；空文件 400；超过 `MAX_UPLOAD_MB` 413；
- 计算 `sha256` 内容指纹——**同内容上传复用同一条 `source_file` 记录**（返回 `deduped: true`，不重写磁盘），血缘场景多个字段常来自同一源文件；
- 存储到 `files/<sha[:2]>/<sha>.<src_type>`，登记原始文件名、大小、上传者、时间。`seed_demo` 走同一服务函数。

### 6.2 清单归一化（`manifest.py`）

三种物理格式（设计方案 §3.4）归一化为同一组 pydantic 记录 `DatasetFieldRecord` / `LineageEdgeRecord`，后续处理与格式无关：

| 格式 | 承载 | 解析函数 | 错误语义 |
|---|---|---|---|
| CSV | 双文件 `datasets.csv` + `lineage.csv`（UTF-8，兼容 BOM） | `read_csv_manifest()` | 行级错误进 `parse_error`；文件级（表头缺失等）整批 400 |
| XLSX | 单工作簿双 sheet `datasets` / `lineage`（sheet 名 strip+lower 匹配） | `read_xlsx_manifest()` | 缺 sheet / 根解析失败整批 400 |
| JSON | 单文件 `{"datasets": [...], "lineage": [...]}`（`src_locator` 为嵌套对象） | `read_json_manifest()` | 根 JSON 解析失败整批 400 |

- `src_locator` 列接受 dict（JSON 清单）或 JSON 字符串（CSV/XLSX 单元格）；
- **行级解析错误不抛出**，写入记录的 `parse_error` 字段，由导入阶段整行拒绝（reason 即行内错误说明），避免一行坏数据导致整批 400；
- `row` 记录清单原始行号（CSV/XLSX 从 2 起、JSON 从 1 起），进入报告 `source_row`。

### 6.3 定位器校验与实文件核查（`locator.py`）

`LOCATOR_MODELS`（`src_type` → pydantic 输入模型）做**结构校验**，`CHECKERS`（`src_type` → checker）打开托管源文件做**实文件核查**并物化 `resolved`（数据模型 §4.1 信封 `{type, input, resolved}`）：

| src_type | 校验/核查要点 | resolved 物化 |
|---|---|---|
| csv | `column`（1-based）/ `header` 二选一；表头名须在首行命中；列号不超列数 | `{column_index, header}` |
| xlsx | sheet 必须存在；`column`（列字母）或 `header_path`（多级表头）二选一；`row_end >= row_start`；**多级表头**按层级逐行匹配、父级合并单元格展开为候选列范围继续下探；**锚点归一**：落在合并区域内的定位物化为左上角锚点 + 合并范围 | `{column_index, column, row_start, row_end, merged_anchors[]}`（`header_path` 路径未给 `row_start` 时默认 `header_rows+1`） |
| json | JSONPath 语法合法且在源文件中至少 1 次命中 | `{hits}` |

核查失败抛 `LocatorError`，导入阶段转为该行 `rejected`（reason 以「实文件核查失败：」开头），**不产生 HTTP 错误**——整批导入照常完成，结果逐条体现在报告。同一套 `CHECKERS`/`LOCATOR_MODELS` 被 M3 `PATCH /fields/...` 的定位器编辑复用（见 §六.6）。

### 6.4 批次落库与导入报告（`import_service.run_import`）

单事务内执行（任何异常整体回滚）：

1. 创建 `import_batch`：`version_no = MAX(version_no)+1`，记录清单文件名（JSON 数组）、格式、操作者；
2. **阶段一 datasets/fields**（先字段后边，满足边表复合外键）：
   - 行级校验：`parse_error`、`dataset_id/field_name` 必填、`src_type` 枚举、`src_file` 引用解析（纯数字→本批绑定文件集内的源文件 ID；否则按原始文件名在绑定集中**唯一定位**，0 命中或多处命中均拒绝）、`src_type` 与源文件实际 `src_type` 一致；
   - 结构校验 + 实文件核查通过后组装定位器信封入库；
   - `_ensure_dataset`：数据集不存在自动创建（写 `dataset added` 日志）；`_upsert_field`：新增→`added`；完全同值→`ok (unchanged)`，不写日志；有差异→`updated`；
3. **阶段二 lineage edges**：`parse_error`、`from_dataset/to_dataset` 必填、**混合字段边（一空一非空）拒绝**、字段级边引用的上下游字段必须存在（本批或已有版本）、数据集必须存在、`confidence` 0~1（默认 1.0）；
   - 同批自然键重复：**后到覆盖** `transform/confidence/note`，报告标 `merged`（设计方案 §3.5-4）；
   - 已存在边：同值 `ok (unchanged)` 不写日志（重导入幂等）；有差异 `updated`——注意此路径会把 `source` 覆写回 `'imported'`（见 §十二-7）；
   - 新边 `source='imported'`，写 `added` 日志；
4. 每条变更写 `change_log`（op + before/after 业务列快照，快照键见 `changes.py`）；
5. 产出 `ImportReport` `{summary: {total, ok, merged, rejected}, items: [{status, kind, ref, reason, source_row}]}`（数据模型 §4.3），序列化存入 `import_batch.report`，随批次详情可下载。

### 6.5 回源预览闭环（`preview.field_preview`）

字段定位卡点击后在系统内直接预览源文件区域（设计方案 §3.6）：返回 `file`（id/原始名/sha256/大小/类型/上传者）+ `verification`（`{status:"passed", version_no, checked_by, checked_at}` 或 `null`——取该字段最近一次 `added/updated` 且关联导入批次的 change_log；导入器只有通过核查才写日志，故该记录即「核查通过」）+ `locator` 信封 + 结构化预览（csv：表头 + 列号 + 前 50 行；xlsx：表头行/合并区域/列/行范围 + 前 50 行；json：命中数 + 前 10 个命中值）。**定位失效**（文件缺失、sheet 改名、行列越界、JSONPath 无命中等）统一抛 `PreviewError`→HTTP 409。

### 6.6 人工纠错中的定位器编辑（设计方案 §七）

`routes/fields.py` `PATCH /fields/{dataset_id}/{field_name}`：可改 `description / field_type / src_locator`；传 `src_locator` 时接受定位器 `input` 或完整信封（`resolved` 一律丢弃重算），**必须重新走结构校验 + 实文件核查 + 重写信封**，任一环节失败 409（中文原因），事务内字段保持原值；成功写 `change_log`（`batch_id=NULL`，op=`updated`）。定位器类型与源文件 `src_type` 不一致返回 409。

## 七、版本与回滚

实现于 `versioning.py` + `changes.py`，规则来自数据模型 §七。核心思想：**当前态直接读写基础表，历史能力全部由 `change_log` 追加日志重建**，不做全量快照。

### 7.1 change_log 追加式记录

- `changes.log_change()`：所有写路径在同一事务内追加日志；快照只含业务列（`FIELD_SNAPSHOT_KEYS` / `EDGE_SNAPSHOT_KEYS`，不含 `id`/时间戳/审计列），保证同实体 before/after 可直接比较、deleted 的 before 可整行重插；
- `edge_key()` 生成多态命名 `<ds>.<field|-->*--><ds>.*`（数据模型 §5.2）；
- 导入路径写 `batch_id=<批次>`；人工编辑写 `batch_id=NULL`，与批次回滚互不干扰。

### 7.2 按批次回滚（`rollback_batch`，admin）

- 批次不存在 404；已回滚（`rolled_back_at` 非空）409；
- 取该批次全部日志按 **id 倒序** 反做：`added`→删除、`updated`→恢复 before、`deleted`→重插 before（`_reverse_log`）；
- 反做遇 `sqlite3.IntegrityError`（外键/唯一冲突，典型场景：更晚批次建的边引用本批字段）→ 整体回滚 + 409「存在后续批次引用本批字段的边，请先回滚更晚的批次」——**批次回滚必须从新到旧线性执行**；
- 成功后写 `import_batch.rolled_back_at/by`；回滚本身不写 change_log。

### 7.3 业务标签（`create_tag` / `list_tags` / `tag_diff`）

- 创建（editor）：`change_seq = 当前 change_log MAX(id)` 锚定日志末尾；`batch_id` 仅信息性记录（取当前最近批次，回滚不依赖它）；重名 409；**不写 change_log**——否则「回滚到更早标签」会把标签当可反做数据删除，违背「标签永久保留」（数据模型 §2.7）；
- diff（viewer）：区间 `(from.change_seq, to.change_seq]` 按 `(entity_kind, entity_key)` 归并——区间首条 before 为起点、末条 after 为终点；起终点均空（先增后删）不计净变更；from 晚于 to 返回 400。

### 7.4 按标签回滚（`rollback_to_tag`，admin，幂等）

- 反做 `id > tag.change_seq` 的**全部**日志（跨批次 + 人工编辑），按 id 倒序；
- **幂等反做**：`_restore_row` 用 `ON CONFLICT ... DO UPDATE` / 先查后写（边自然键含 NULL，部分唯一索引不能作 ON CONFLICT 目标），`_delete_row` 天然幂等——重复回滚安全，最终状态不变；
- 审计列还原：重插边时 `created_by` 优先从该自然键在本次 deleted 日志**之前最近一条 added 日志的 actor** 还原（缺失退回回滚执行者），`updated_by` 记回滚执行者；
- 被反做日志所属批次同步 `COALESCE` 写 `rolled_back_at/by`（重复回滚保留首次时间；标签只在批次事务之间创建，不会切分单个批次）；
- **审计**：每次调用追加一条 `rollback_record`（tag_name、区间 from/to、reverted 条数、actor、时间）——回滚本身不写 change_log，否则下次回滚会反做「回滚日志」破坏幂等（数据模型 §2.10）。

### 7.5 写入与留痕矩阵

各写操作是否写 change_log、审计落点，见数据模型 §9.4（标注只增不改不写日志；字段/边人工编辑写日志；标签创建与回滚不写日志、分别落在 `version_tag` 与 `rollback_record`）。标注（annotation）不参与回滚，永久保留。

## 八、AI 模块（M4）

对应设计方案 §六（AI 对话）与 §6.4「AI 优化的两条路径」。安全基线：**AI 只有只读查询能力 + 低置信候选建议，候选必须人工确认才生效**（业务不变量#4）。

### 8.1 OpenAI 兼容客户端（`ai/llm.py`）

- 纯 `urllib.request` 直连 `{LLM_BASE_URL}/chat/completions`（`endpoint_url` 兼容 `https://host/v1` 与写全的 `.../chat/completions` 两种写法）；供应商、密钥、模型经仓库根 `.env` 配置，密钥永不入库、API 永不回显；
- `is_configured()`：`LLM_BASE_URL` 与 `LLM_MODEL` 均非空才算已配置（`LLM_API_KEY` 可空，兼容本地无鉴权服务）；
- `tools` 为空时不发送 `tools`/`tool_choice`（用于收口回答）；超时 60s；
- 错误分类：`LLMNotConfigured`（路由转 **503**）与 `LLMError`（HTTP 非 200 / 不可达 / 响应结构不合法，路由转 **502**）；
- `GET /ai/status` 返回 `{configured, model}`（未配置时 `model=null`），未配置时 `POST /ai/chat` 返回 503（`NOT_CONFIGURED_MESSAGE` 提示配置方法）。

### 8.2 只读工具集（`ai/tools.py`，5 个）

`TOOL_SCHEMAS`（OpenAI function calling JSON Schema）+ `TOOL_FUNCS`，全部只读、不写库，每个函数接收 `sqlite3.Connection` 由 `chat.py` 每轮打开：

| 工具 | 实现 | 说明 |
|---|---|---|
| `search_fields` | `LIKE` 匹配 dataset_id / 数据集名 / 字段名 / 字段描述 / 字段标注（数据模型 §3.2 的轻量实现，无 FTS5）；排序：精确=前缀>其余；`LIMIT 20` | 按关键词定位字段 |
| `get_field_details` | 字段元数据 + 定位器信封 + 源文件信息 + 标注 + 回源预览（复用 `preview.field_preview`；预览失败降级为 `{"error": ...}` 不阻断详情） | 回答「字段来自哪个文件/哪一列」 |
| `trace_lineage` | 复用 `lineage.lineage_subgraph`（direction=both/up/down 合并上下游两方向，hops 1~5） | 回答「从哪来/流向哪里」，返回 GraphPayload 供前端联动出图 |
| `get_field_history` | 字段 change_log 倒序 `LIMIT 50`（复用 `changes.load_snapshot`） | 「谁在何时改了什么」 |
| `mark_highlight` | 校验 `fields` 中每个 `{dataset, field}` 存在性（SELECT）、去重，上限 `MAX_HIGHLIGHT_FIELDS=8`；无效项记入 `ignored` 回传，全部无效抛 `ToolError` | **画布联动信号**：声明要高亮的字段，不返回业务数据（2026-10-24 新增，见 [06_AI画布联动高亮修复](./06_AI画布联动高亮修复.md)） |

参数/目标不合法抛 `ToolError`，以 `{"error": ...}` 回传 LLM 自我纠正，**不中断对话**。

### 8.3 启发式血缘建议（`ai/suggest.py`）

**不调用 LLM，可离线运行**（设计方案 §6.4 路径 2 的轻量实现）：

1. 字段名归一化（`lower` + 去下划线）：完全相等 → `confidence=0.7`；包含关系（较短一方 ≥3 字符）→ `0.6`；
2. 候选方向：请求给出的数据集/字段为上游（from），**其他数据集**的相似字段为下游（to）；
3. 排除已存在边（正反两个方向都排除，避免建议出反向重复/环）与本次已见键；按置信度降序、同置信度稳定排序，上限 20 条；
4. 候选以 **`source='ai'` 落库**并写 `change_log(added)`——重复调用同自然键跳过，不重复落库；
5. 闭环（均按四元自然键定位，仅 `source='ai'` 的候选可操作，否则 404）：
   - `POST /ai/suggest/confirm`（editor）：`source` 改 `manual`，写 `updated` 日志；
   - `POST /ai/suggest/reject`（editor）：删除候选边，写 `deleted` 日志，返回 204。

### 8.4 对话编排（`ai/chat.py`，function calling）

- system 提示**由后端固定**（`SYSTEM_PROMPT`：工具说明 + 「必须基于工具数据作答、不得编造」「无写权限」「需要高亮时先调 mark_highlight」），前端只传 user/assistant 历史（`AiChatMessage.role` 限定二者），可选 `focus={dataset, field}` 追加聚焦上下文；
- 循环：调 `llm.complete(messages, tools)` → 模型返回 `tool_calls` 时逐个执行只读工具、结果以 `role=tool` 消息追加，继续下一轮；不再请求工具时取 content 为最终 `answer`；
- **有界性**：最多 5 轮工具调用（`MAX_TOOL_ROUNDS=5`），第 6 次请求不带 tools 强制收口；
- 返回 `{answer, tool_trace: [{tool, args, ok}], graph?, highlights?}`——`graph` 取最后一次 `trace_lineage` 返回的 GraphPayload，供前端画布联动渲染；`highlights` 汇总 `mark_highlight` 声明的字段（跨调用去重、上限 8），供前端画布红色追踪链联动；
- 工具参数 `arguments` 兼容 dict / JSON 字符串两种供应商形态；content 兼容字符串与分段数组。

## 九、错误处理约定

- **统一形态**：路由层抛 `HTTPException(status, detail)`，detail 为**中文可读原因**（前端直接回显，如 409 定位核查失败原因）。服务层不直接抛 HTTP 异常，而是抛领域异常由路由转换：

| 服务层异常 | 路由转换 | 典型场景 |
|---|---|---|
| `LookupError`（含 `LineageNotFound`） | 404 | 数据集/字段/边/批次/标签/源文件/AI 候选边不存在 |
| `PreviewError` | 409 | 回源预览定位失效（文件缺失、sheet 改名、行列越界、JSONPath 无命中） |
| `LocatorError` | 不抛 HTTP——导入报告内行级 `rejected`；`PATCH /fields` 核查失败则 409 | 实文件核查失败 |
| `ValueError`（业务规则） | 400 或 409（按语义） | 标签重名 409、`from` 晚于 `to` 的 diff 400、批次已回滚 409、回滚引用冲突 409 |
| `LLMNotConfigured` / `LLMError` | 503 / 502 | 未配置 LLM / LLM 上游错误 |
| `sqlite3.IntegrityError` | 409（服务层捕获转 `ValueError`） | 回滚遇外键/唯一冲突；`POST /edges` 并发重复由唯一索引兜底转 409 |

- **状态码语义**：401 缺少/无效 Bearer 凭据或用户已删除；403 角色不足（`require_role`）；400 请求结构/格式/参数错（含混合字段边、清单缺文件）；404 目标不存在；**409 业务冲突**——定位器核查失败（PATCH 字段）、字段被改/源文件类型不符、边自然键已存在、批次已回滚、回滚引用完整性冲突、标签重名、用户名重复；413 单文件超 `MAX_UPLOAD_MB`；422 子图参数越界（`hops`/`direction`，FastAPI Query 校验与 `lineage.py` 手工校验双保险）；502/503 仅用于 LLM。
- **行级 vs 整批**：导入清单的行级错误（解析/校验/核查）**不产生 HTTP 错误**，进导入报告逐条 `rejected` + 原因 + 行号；文件级错误（缺 sheet、根 JSON 解析失败、格式不符）整批 400。
- **事务保障**：所有写操作在 `with get_db()` 单事务内，异常自动回滚（如定位器核查失败时字段保持原值）。

- 部署形态：单进程 uvicorn；CORS 由 `CORS_ORIGINS` 显式配置（认证走 Bearer 头而非 Cookie，`allow_credentials=False`）。

## 十二、已知差异与注意事项

以下为撰写本文时发现的设计文档与代码不一致点、或设计文档未显式覆盖的代码行为（编号便于引用）：

1. **FTS5**：设计方案 §二（非目标）与 §八架构图写「SQLite (FTS5 搜索)」，实现未引入 FTS5，`search_fields` 用 `LIKE` 全表扫描（数据模型 §3.2 已记录该取舍，设计方案未同步更新）。
2. **AI 工具集**：设计方案 §6.2 列 6 个工具（含 `trace_upstream` / `trace_downstream` / `get_subgraph` / `suggest_lineage`）且描述为「薄封装 REST」（对应 `GET /search`、`GET /fields/{ds}.{f}`、`GET /lineage/trace` 等）；实现收敛为 4 个**内部 Python 工具**（`trace_lineage` 合并上下游/子图三能力），未提供对应独立 REST 端点，建议生成走独立启发式端点 `/ai/suggest` 而非 LLM 工具（数据模型 §9.3 已按实现收敛，设计方案 §6.2 未更新）。
3. **seed_demo 执行目录**：`seed_demo.py` docstring 写 `cd backend`，实际为 `prototype/backend`（README 正确）。
4. **edge 唯一约束**：设计方案 §4.1 DDL 只有 `UNIQUE(四列)`；实现额外建 `uq_edge_field` / `uq_edge_table` 两个部分唯一索引（数据模型 §2.5 已说明，属已文档化的 M1 增量）。
5. **`.env.example` 未列 `MAX_UPLOAD_MB`**：`Settings` 支持（默认 50MB）但模板未包含该键，使用者需自行追加才能覆盖。
6. **`GET /lineage/snapshot`**：M1 验证端点定义在 `routes/imports.py`（路径前缀属 lineage），README API 一览未列出；M2 起主查询能力为 `GET /lineage/subgraph`。
7. **重导入覆写 `source`**：`import_service` 阶段二对已存在且内容有差异的边执行 `UPDATE ... source='imported'`——若某边此前是人工边（`manual`）或已确认的 AI 边，清单重导入同自然键会将其来源改回 `imported`。设计文档未规定重导入时 `source` 的归并规则，[TBD-BIZ] 是否应保留原 `source`，由产品在下一里程碑确认。
8. **admin「删除数据集 / 重置导入」**（设计方案 §4.4）与用户角色逐行修改（README 已知差距，`[TBD-BIZ]`）在原型中未实现，用户管理仅列表 + 新增。
