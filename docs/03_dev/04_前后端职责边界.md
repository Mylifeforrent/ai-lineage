# 前后端职责边界（Clew）

> 本文约定 `prototype/frontend`（React SPA）与 `prototype/backend`（FastAPI + SQLite）各自承担的职责与安全边界，作为后续演进、评审与新增功能的划分依据。结论只描述当前原型已实现的行为；差距见 §九。

---

## 一、引言与定位

Clew 是「单进程 + 单关系库」的字段级血缘工具（设计方案 §八），前端是纯消费方：只通过 REST/JSON（JWT 鉴权）读写后端，不直连数据库、不解析源文件。本文回答四个问题：

1. 哪些校验与不变量由后端强制、前端仅做 UX 优化；
2. 每个功能域（认证、导入、编辑、版本、AI 等）前后端各做什么、错误如何分工；
3. AI 能力的读写边界在哪里（工具只读、建议须人工确认）；
4. 当前已知差距中哪些属于边界未闭合（如用户角色变更接口缺失）。

## 三、边界总原则

以下原则均可追溯到上述材料，是后文职责矩阵与禁止事项（§八）的推导起点。

| # | 原则 | 依据 |
|---|---|---|
| P1 | **后端 SQLite 是唯一可信数据源**：当前态直接读写基础表，一切历史能力（diff/回滚）由 `change_log` 推导；前端不持有也不裁决任何持久状态 | 数据模型 §七；设计方案 §4.2 |
| P2 | **全部九条业务不变量由后端保证**（无定位不入库、定位归一化、边唯一、AI 不可直接生效、标注只增不改、写必留痕、版本可回退、权限分级、密钥不入库）；前端可以「帮助用户少犯错」，但不参与任何不变量的强制 | 业务模型 §六；落点见数据模型 §八 |
| P3 | **权限永远以后端 `require_role` 守卫为准**：每个路由声明最低角色（viewer < editor < admin），角色取数据库当前值；前端按角色隐藏写入口只是 UX，不是安全边界 | 设计方案 §4.4；`prototype/backend/src/lineagelite/security.py`（`require_role` 注释「角色以数据库当前值为准」）；`prototype/frontend/src/lib/roles.ts`（注释「真正的权限校验始终在后端」） |
| P4 | **操作者身份不可伪造**：`change_log.actor`、`annotation.author`、各表 `created_by` 一律取自 JWT `sub`，前端无任何字段可指定 | 业务模型 §六-6；设计方案 §4.4（「author/actor 均取自 JWT，不可伪造」） |
| P5 | **实文件核查与定位器物化只发生在后端**：`src_locator.resolved` 由后端对托管源文件解析写入，前端传入的 `resolved` 一律丢弃重算 | 数据模型 §四-4.1；`prototype/backend/src/lineagelite/routes/fields.py` 模块注释 |
| P6 | **唯一渲染入口**：所有「取子图」能力统一返回 `GraphPayload`，搜索出图、点击展开、AI 对话出图共用前端同一渲染路径，前端不维护第二套图数据结构 | 设计方案 §5.2；`prototype/frontend/src/components/Workspace.tsx`（`applyGraph` 同时服务常规子图与 AI 出图） |
| P7 | **无推送，纯请求-响应**：后端不维护任何 UI 状态（折叠、过滤、选中），写操作后由前端主动重新拉取刷新 | 设计方案 §八（同步写、无消息队列）；前端各组件写成功后 `refreshGraph/refreshAll` |
| P8 | **密钥与存储路径永不离开后端**：LLM 密钥只在部署环境 `.env`；源文件 `storage_path` 不出现在任何 API 响应中，下载/预览走受控接口 | 业务模型 §六-8/9；`prototype/backend/src/lineagelite/routes/files.py`、`routes/ai.py` |

## 四、职责矩阵

每域四列：前端职责 / 后端职责 / 不变量与校验归属（后端服务层 / 数据库约束 / 前端不参与）/ 错误处理分工（谁拦截、怎么展示）。通用约定：所有请求经 `prototype/frontend/src/lib/api.ts` 的 `request()` 封装，携带 `Authorization: Bearer <token>`；401 全局处理见 §五；写入口的显隐由 `isEditor/isAdmin`（`lib/roles.ts`）控制。

### 4.1 认证与 Token 生命周期

| 前端职责 | 后端职责 | 不变量与校验归属 | 错误处理分工 |
|---|---|---|---|
| 登录表单（`LoginPage`）；会话 `{access_token, username, role}` 持久化到 `localStorage`（`SESSION_STORAGE_KEY`）；登出即 `clearSession`；任意带 token 请求收到 401 时派发 `AUTH_EXPIRED_EVENT` 并由 `App.tsx` 清会话回登录页 | `POST /auth/login` 校验 pbkdf2 口令哈希并签发 JWT（HS256，`exp = jwt_expire_hours`）；每个受保护路由经 `current_user` 解码 Bearer token，再经 `require_role` **回查数据库角色**（角色被变更后旧 token 立即按新角色生效，`security.py`） | 口令只存加盐哈希（设计方案 §4.1 `user.password_hash`）；token 有效性、过期、角色全部后端判定，前端不解析 JWT 内容、不做本地过期计时 | 后端 401（「用户名或密码错误」，不区分用户不存在与密码错；token 无效/过期；用户已删除）；前端 `request()` 拦截 401→全局回登录页（§五），登录失败原因展示在登录表单 |

### 4.2 用户管理（RBAC）

| 前端职责 | 后端职责 | 不变量与校验归属 | 错误处理分工 |
|---|---|---|---|
| `UserManagementModal`：用户列表、新增用户（创建时角色三选一）；TopBar 的入口仅 `admin` 可见（`isAdmin`）。表单内做轻校验（用户名 ≥2 字符、密码 ≥6 位）并与 UI 标注「当前接口仅支持新增用户，角色变更未提供」 | `GET/POST /users`（`require_role("admin")`）：用户名查重重名 409；`UserCreate` pydantic 约束 `username` 2~64、`password ≥6`、`role` 必须匹配 `^(admin\|editor\|viewer)$`（`models.py`） | 角色值域：pydantic pattern + `user.role CHECK`（数据库约束）；`username UNIQUE`（数据库约束）；「至少保留一名 admin / 管理员能否改自己角色」**无任何一层强制**，见 §九 [TBD-BIZ] | 非 admin 调用被后端 403（UI 已隐藏入口，403 是兜底）；409 重名由 `readErrorDetail` 取 `detail` 原文回显在表单错误区 |

### 4.3 源文件托管与下载

| 前端职责 | 后端职责 | 不变量与校验归属 | 错误处理分工 |
|---|---|---|---|
| 当前原型**无上传 UI 入口**（前端未实现导入向导，见 §九）；已托管文件的下载在 `PreviewModal` 经 `downloadSourceFile` 走受控接口（blob 保存，只传文件 ID，不经手存储路径） | `POST /files`（editor）：扩展名白名单 csv/xlsx/json、大小上限 `max_upload_mb`、按 sha256 内容去重复用记录、落盘 `data/files/`；`GET /files`（viewer）列表；`GET /files/{id}/download`（viewer）受控 `FileResponse` | 同内容只存一份：`source_file.sha256 UNIQUE`（数据库约束）；存储路径不对外暴露：`storage_path` 不出现在响应中，下载按 ID 经鉴权（业务规则 #8，`routes/files.py` 注释）；`src_type` 值域 CHECK | 后端 400（扩展名/大小）、404（ID 不存在）；前端下载失败走 `ApiError`，401 同样触发全局登出 |

### 4.4 导入（CSV/XLSX/JSON 三格式 + 核查）

| 前端职责 | 后端职责 | 不变量与校验归属 | 错误处理分工 |
|---|---|---|---|
| 无 UI 入口（原型未实现导入向导；演示数据由 `seed_demo` 生成）。[TBD-FE] 导入向导三步流（传源文件→传清单→报告）属后续前端职责，UI 基线见低保真原型「导入向导」屏 | `POST /import`（editor）：`format` 白名单、`source_file_ids` 存在性 404、按格式读清单（`read_csv/xlsx/json_manifest`）；`run_import` 完成结构校验 → **打开托管源文件实文件核查定位器** → 引用校验 → 冲突合并，事务内全部入库为新批次并写 `change_log`，生成逐条 `report`（summary + items，含 rejected 原因与原始行号，数据模型 §四-4.3） | 无定位不入库（#1）：核查失败该字段拒绝导入，`resolved` 由导入器物化（后端服务层）；定位归一化（#2）：合并单元格锚点、多级表头展开（后端 `locator.py`）；边唯一（#3）：数据库部分唯一索引兜底；写必留痕（#6）：批次 + 日志同事务 | 结构性错误（格式不合法、清单为空、文件不存在）由路由抛 400/404，`detail` 为中文原因；**逐条成败不在 HTTP 状态码里**，而在 201 响应的 `report` 中——这是给未来导入向导的呈现契约；核查失败的字段拒绝入库但不使整批失败（报告 rejected） |

### 4.5 数据集 / 字段查询

| 前端职责 | 后端职责 | 不变量与校验归属 | 错误处理分工 |
|---|---|---|---|
| `DatasetSidebar` 数据集搜索/选择（本地按 `field_names` 过滤，不发请求）；`DetailPanel` 展示字段详情（描述/类型/定位器人类可读形式） | `GET /datasets`（viewer，每项含 `field_names` 供双类搜索目标——数据模型 §9.1 契约增量）；`GET /datasets/{id}` | 无写路径，无不变量；工作区内所有数据集对所有用户可见（不做对象级授权，业务模型 §二） | 后端 404；前端列表加载失败展示错误条与重试按钮（`datasetsError` + `onRetry`） |

### 4.6 血缘子图查询

| 前端职责 | 后端职责 | 不变量与校验归属 | 错误处理分工 |
|---|---|---|---|
| 选择种子数据集 + 跳数（`HOP_OPTIONS` 1~5，与后端 `Query(ge=1, le=5)` 对齐）拉取子图；dagre 分层布局渲染；**本地过滤**（最低置信度 / 隐藏 AI 边 / 仅已确认）只裁剪显示、不改动后端返回的数据（`Workspace.tsx` 注释）；AI 出图与常规子图共用 `applyGraph` | `GET /lineage/subgraph`（viewer）：递归 CTE 一次取全子图（`lineage.py`），天然 hydrate 无 N+1（设计方案 §4.3）；`GraphPayload.edges[]` 携带数据库主键 `id` 供 M3 编辑定位（§9.1） | 图查询单路径（后端）；跳数上限由后端 `Query` 强制，前端选项只是镜像 | 后端 404（种子不存在）、422（参数非法，如字段级跳数组合）；前端 `graphError` 面板回显 `detail`；请求竞态由 `AbortController` 取消旧请求 |

### 4.7 回源预览

| 前端职责 | 后端职责 | 不变量与校验归属 | 错误处理分工 |
|---|---|---|---|
| 字段详情定位卡（源文件名 + `humanizeLocator` 人类可读定位）；`PreviewModal` 渲染后端返回的结构化预览（csv 列/行、xlsx 表头路径与合并区域、json 命中值）并高亮对应区域 | `GET /fields/{dataset_id}/{field_name}/preview`（viewer）：读**托管源文件**按定位器切片，响应含 `file`（元信息，不含存储路径）、`verification`（最近一次通过实文件核查的版本/操作者/时间，§9.1）、`locator`、`preview` | 预览必须基于托管文件 + 后端定位器，前端不得自行取文件解析（P5/P8）；viewer 即可预览（业务模型 §二：viewer 的合法活动） | 后端 404（字段不存在）、**409（定位失效，`PreviewError`）**；前端 `PreviewErrorState` 保留 `status + message` 分态展示，提示定位器已失效而非静默空白 |

### 4.8 字段编辑（描述 / 类型 / 定位器 + 重新核查）

| 前端职责 | 后端职责 | 不变量与校验归属 | 错误处理分工 |
|---|---|---|---|
| `DetailPanel` 编辑表单：按 `src_locator.type` 动态渲染三种定位器输入，`buildLocatorInput` **只提交 `input`**；描述/类型为普通文本框；编辑入口 `canEdit` 才显示；保存按钮文案明示「后端会重新核查，失败 409 保留原值」 | `PATCH /fields/{dataset_id}/{field_name}`（editor）：空请求体 400、`src_locator` 显式传 null 400（字段必须始终可回源）；改定位器时**重新结构校验（pydantic）→ 打开源文件实文件核查 → 重写整个信封**（前端传的 `resolved` 被丢弃），`type` 与源文件 `src_type` 不一致 409；成功写 `change_log(updated, batch_id=NULL, actor=当前用户)` | 无定位不入库（#1）的编辑路径延续：定位器不可清空、核查不通过字段保持原值（事务内未写入即返回，`routes/fields.py`）；`resolved` 物化只归后端（P5）；写必留痕（#6） | 后端 404 / 400 / 409（`detail` 为中文原因，如「实文件核查失败：…」）；前端将 `ApiError.message` **原文回显**在表单错误区（409 原因回显），不重写文案 |

### 4.9 血缘边增删改（manual 人工边）

| 前端职责 | 后端职责 | 不变量与校验归属 | 错误处理分工 |
|---|---|---|---|
| `LineageCanvas` 拖拽字段/表级 handle 产生 `EdgeDraft`（`nodesConnectable/connectable` 由 `canEdit` 控制）→ `EdgeCreateModal` 提交；`EdgeDetailPanel` 编辑 `transform/note/confidence`（0~1 前端校验）、删除先过 `ConfirmDialog`，确认框明示「删除会写入变更日志；可由管理员回滚到之前的版本标签恢复」 | `POST /edges`（editor）：`source` 由后端**强制写 `manual`**（不接受前端指定 source）；字段级/表级必须二选一 400；`EdgeCreate.confidence` pydantic `ge=0 le=1`；同自然键 409。`PATCH /edges/{id}`（editor）：仅 `transform/note/confidence` 可改，**endpoints 与 source 不可改**。`DELETE /edges/{id}`（editor）：204，写 `deleted` 日志 | 边唯一（#3）：应用层静态校验 + `uq_edge_field` / `uq_edge_table` 部分唯一索引兜底并发（数据模型 §9.5）；`source` 值域 `CHECK(imported/manual/ai)`（数据库约束）；写必留痕（#6）：POST/PATCH/DELETE 均写 `change_log`（数据模型 §9.4） | 后端 400（二选一/空体/confidence 越界）、409（重复边）、404（边不存在）；前端区分场景：表单类错误回显编辑区、动作类错误走 Toast；成功后刷新子图并提示「人工补边」 |

### 4.10 标注（追加式）

| 前端职责 | 后端职责 | 不变量与校验归属 | 错误处理分工 |
|---|---|---|---|
| `AnnotationSection`（字段/边详情内）：按目标拉取与追加展示；输入框 `canEdit` 才显示 | `POST /annotations`（editor）：目标存在性**应用层校验**（dataset 查 id、field 查复合自然键、edge 按数据模型 §5.2 格式解析四元自然键），不存在 404、格式非法 400；`GET /annotations`（viewer）按 `target_kind/target_id` 过滤，id 升序 | 标注只增不改（#5）：**无更新/删除接口**，前端也无入口（与业务模型一致，README 已知差距第二条）；标注不写 `change_log`、不随回滚删除（数据模型 §七/§9.4，审计落点为 `annotation.author/created_at`） | 后端 400/404；前端在标注区内联回显 `detail`；目标被回滚删除后新增标注将得到 404，由文案解释 |

### 4.11 变更历史

| 前端职责 | 后端职责 | 不变量与校验归属 | 错误处理分工 |
|---|---|---|---|
| `HistoryDrawer`（字段/边详情的「变更历史」入口）：只读展示 op / 前值 / 后值 / 操作者 / 时间 | `GET /changes`（viewer）：按 `entity_kind + entity_key` 过滤，id 倒序，`limit` 默认 50、上限 500（`Query` 强制）；`before/after` 返回**解析后的 JSON 对象**（§9.2），前端无需再解 TEXT | 写必留痕（#6）由后端所有写路径保证，历史接口本身只读、无不变量；快照键集合固定（`changes.py` 的 `FIELD_SNAPSHOT_KEYS/EDGE_SNAPSHOT_KEYS`，数据模型 §四-4.2） | 后端参数越界 422（pydantic）；前端加载失败在抽屉内回显；无写路径故无冲突处理 |

## 五、认证与授权边界（专节）

1. **签发与校验全归后端**：JWT 签发（`create_token`，HS256 + `exp`）、Bearer 解码（`current_user`）、角色判定（`require_role`）都在 `prototype/backend/src/lineagelite/security.py`。关键实现细节：`require_role` **每次请求回查 `user.role` 数据库当前值**，JWT 中的 role 仅是登录时快照——因此（未来的）角色变更接口落地后，旧 token 的权限立即收紧，无需等待过期。
2. **前端持有 token 的职责与风险**：`lib/api.ts` 将 `Session`（含 `access_token`）以明文 JSON 存于 `localStorage`（key `clew.session`），页面刷新后恢复会话；登出/过期时清除。这是原型的明确取舍（README M3 节）：风险是同源 XSS 脚本可读取 token；原型未引入 httpOnly Cookie / refresh token 机制（该风险与缓解属后续演进决策，[TBD-FE]）。
3. **401 全局处理链路**：任意携带 token 的请求收到 401 → `request()` 派发 `AUTH_EXPIRED_EVENT`（`downloadSourceFile` 的独立 fetch 路径同样处理）→ `App.tsx` 监听后 `clearSession` 并切回 `LoginPage`，提示「登录已过期，请重新登录后继续」。前端**不做本地 token 过期预测**，以后端 401 为唯一过期信号。
4. **viewer 的 UI 隐藏 vs 后端强制**：`lib/roles.ts` 的 `isEditor/isAdmin` 只决定写入口是否渲染（画布 `nodesConnectable`、编辑/删除按钮、打标签表单、回滚按钮、用户管理入口、AI 确认按钮）。**前端隐藏不是安全边界**：直接以 viewer token 调用写接口会被后端 `require_role` 拒绝（403「需要 X 及以上角色」）；前端对该兜底 403 有统一文案（`readErrorDetail`：「当前账号无权执行此操作」）。评审任何新功能时，判断标准是「去掉前端后权限是否仍然成立」。
5. 角色层级固定为 `viewer < editor < admin`（`ROLE_ORDER`），与设计方案 §4.4、业务模型 §二一致；不做对象级 ACL（工作区内所有数据集可见，`[TBD-BIZ]` 数据集级私有化见设计方案 §十剩余待定项）。

## 六、数据契约边界

1. **类型对应**：前端 `prototype/frontend/src/types.ts` 与后端 `models.py`（请求侧 pydantic：`UserCreate`、`FieldPatch`、`EdgeCreate/EdgePatch`、`AnnotationCreate`、`VersionTagCreate`、`AiChatIn/AiSuggestIn/AiEdgeKeyIn`）及各路由的响应 dict 一一对应。命名约定：字段名保持 snake_case 原样传输（如 `from_dataset`、`field_count`），前端不做 camelCase 转换。代表性对应：`Session ↔ TokenOut`（`/auth/login` 响应）、`DatasetSummary ↔ GET /datasets`（含契约增量 `field_names`）、`LineageGraph/LineageEdge ↔ GraphPayload`（`edges[].id` 为数据库主键，M3 编辑按它定位，数据模型 §9.1）、`PreviewResponse ↔ /fields/.../preview`（含 `file/verification` 增量）。
2. **时间与 ID 序列化**：后端时间一律为 UTC ISO 8601 字符串（`isoformat(timespec="seconds")`，如 `routes/files.py`、`changes.py` 的 `now()`），前端只做展示格式化（`lib/format.ts` 的 `formatDateTime`），不做时区换算以外的解析假设。ID 分三类并约定传输形态：dataset 用用户自定义字符串 `id`；edge 同时有自增主键 `id`（编辑/删除用）与四元自然键（AI confirm/reject 用，`AiEdgeKeyIn`）；实体历史/标注目标用数据模型 §5.2 的 `entity_key` 字符串（`ds.field`、`from-->to`，表级可省略 `.*`）——前端 `lib/entities.ts` 的 `edgeEntityKey` 负责拼装，但**合法性最终由后端应用层校验**（多义 400）。
3. **错误响应结构**：后端错误体为 FastAPI 标准 `{detail: <string>}`；参数校验失败时 `detail` 为 pydantic 数组 `[{loc, msg, ...}]`。前端 `readErrorDetail`（`lib/api.ts`）统一消费：优先取字符串 `detail` 原文；数组则拼接各 `msg`（`；`分隔）；缺失时按状态码给中文兜底（401/403/404/409/422 各有固定文案）。**409 原因回显是明确的前端职责**：字段定位器核查失败（§4.8）、边重复、标签/用户名重名的冲突场景，后端 `detail` 均为完整中文原因，前端原样呈现、不改写。
4. **契约演进规则**：代码相对设计方案 §四的增量以数据模型 §九为准（M2/M3/M4 三批），新接口必须同步登记，避免文档与 `prototype/backend/src/lineagelite/` 漂移。字段级的完整请求/响应表不在本文重复，见 ./05_API接口文档.md；部署与模块结构见 ./01_架构设计.md。

## 七、AI 边界（专节）

1. **工具只读**：`/ai/chat` 暴露给模型的工具集为 `search_fields`、`get_field_details`、`trace_lineage`、`get_field_history`（`prototype/backend/src/lineagelite/ai/tools.py`），全部为对 SQLite 的只读查询，不写库（数据模型 §9.3）。对话本身（viewer+）不可能产生任何数据变更。
2. **system 提示归属后端**：模型 system 提示由后端固定拼装（含可选 focus 上下文），`AiChatMessage.role` 限定 `user/assistant`——前端无法注入指令覆盖工具约束（`models.py` 注释「避免前端覆盖工具约束」；`AiAssistantDrawer.tsx` 注释「system 提示由后端固定」）。
3. **`source='ai'` 的可见性与呈现**：AI 候选边是真实的 edge 行（低置信、`source='ai'`），随子图正常下发；前端以 `SourceBadge` 区分来源，并提供「隐藏 AI 边 / 仅已确认 / 最低置信度」**纯本地过滤**（不请求后端、不删数据）。设计方案 §5.1 的「隐藏 AI 低置信边」过滤由前端实现，这是少数明确划给前端的「呈现层不变量」——只影响显示，不影响回滚/确认语义。
4. **确认转正与拒绝删除的分工**（业务流程 §5.6 / 数据模型 §9.3）：
   - 前端：入口在边详情（不依赖内存中的候选卡片，刷新后仍可操作）；确认按钮仅 editor+ 可见；成功后刷新使 `source` 变为 `manual`。
   - 后端：`confirm` 把 `source='ai'` 改写为 `manual` 并写 `updated` 日志——**「editor 以上人工确认」这一不变量（#4）由后端角色守卫强制**；`reject` 删除候选边并写 `deleted` 日志（等价于普通删边，可被标签回滚恢复）。
   - 边界含义：AI 永远不直接产生正式血缘；「确认」是一次普通的人工写操作，复用边的留痕与回滚机制。
5. **密钥与配置**：LLM 密钥只存在于部署环境 `.env`（业务规则 #9），`/ai/status` 只回报 `configured/model`；未配置时 `/ai/chat` 返回 503，前端据此引导配置而非报错重试。

## 八、禁止事项清单

由 §三 原则推导，评审时按 Checklist 执行（Pass/Fail）。

**前端禁止：**

1. 禁止解析源文件或自行物化定位器（`resolved` 永远由后端计算，前端传入也会被丢弃）——P5。
2. 禁止把角色隐藏当作权限兜底（隐藏入口 ≠ 禁止操作；一切权限以后端 403 为准）——P3。
3. 禁止伪造/指定操作者（不传 `actor/author/created_by` 类字段，一律由后端从 JWT 取）——P4。
4. 禁止在前端拼接 `source`、`role` 等受控字段的默认值以绕过语义（建边 `source='manual'` 由后端强制；用户 `role` 由后端 pattern 校验）。
5. 禁止本地计算 diff / 回滚结果替代后端接口（`change_log` 归并、反做幂等性只在后端保证）——P1。
6. 禁止在 AI 请求中注入 system 角色消息或伪造工具调用轨迹（role 只能 `user/assistant`）。
7. 禁止缓存会话绕过 401（收到 401 必须走全局登出链路，不得静默重试）。

**后端禁止：**

1. 禁止在任何响应中返回 `storage_path`、文件系统绝对路径或 LLM 密钥/配置值——P8。
2. 禁止提供绕过 `require_role` 的写路由；新增路由必须声明最低角色——P3。
3. 禁止接受前端指定的操作者身份；禁止写操作不落 `change_log`（标注创建、标签创建/回滚按数据模型 §9.4 的白名单除外）——P2/P4。
4. 禁止维护或询问 UI 状态（折叠、过滤、选中、Toast）；后端只认请求参数——P7。
5. 禁止引入推送通道改变请求-响应模型（演进需先修订本边界文档与 ./01_架构设计.md）。
6. 禁止让 `resolved` 的计算脱离托管源文件（核查必须打开 `data/files/` 中的实文件）——P5、业务规则 #1。
