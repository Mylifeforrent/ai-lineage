# 07 · AI 模块演进规划（2026-10-24 定稿）

> 定位：AI 模块从「对话查询器」到「治理 copilot」的演进蓝图与已确认决策记录。
> 结论先行：**选 LangChain、不引入 LangGraph**；自动补描述走「草稿 → 人工确认 → annotation」；暴露 MCP server。
> 关联：[06_AI画布联动高亮修复](./06_AI画布联动高亮修复.md)（上一轮修复）、[03_后端开发文档](./03_后端开发文档.md) §八、[02_前端开发文档](./02_前端开发文档.md) §七。

## 一、背景与差距判断

上一轮评估（2026-10-24）确认了三层断层，本规划逐项落地：

1. **体验层**：`llm.py` 为 urllib 同步阻塞（60s 超时），提问后白等 20–40s 无反馈——业界 agent chat 的第一原则是流式反馈（LangChain「UX for Agents」、OpenMetadata AI SDK 的 stream 接口均为此）；
2. **能力层**：只能「查」不能「改」——设计方案 §6.2 规划的对话内 `suggest_lineage` 未接入；血缘建议只有同名/包含两条规则（设计方案 §6.4 规划的「语义相似 + LLM 判断」未做）；描述空缺没有 AI 辅助补全；缺影响分析问答；
3. **工程层**：LLM 客户端手写 urllib 不可换供应商、无评估集、未对外暴露工具。

外部参照：OpenMetadata 1.8 将元数据/血缘封装为 **MCP server** 供任意 agent 消费；Atlan 的 AI 自动生成描述采纳率约 70%、并把列级影响分析作为 agent 核心场景；Atlan AI Labs 基准显示目录上下文可把 text-to-SQL 准确率相对提升 38%（治理上下文有价值，但 text-to-SQL 超出本产品边界，**明确不做**，见 §五）。

## 二、已确认决策（2026-10-24，用户拍板）

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| D1 | LLM 接入层 | **升级为 LangChain**（`langchain-openai` 的 `ChatOpenAI` + `OpenAIEmbeddings`），替换手写 urllib 客户端 | 统一封装「OpenAI / 阿里云 DashScope 兼容模式」双供应商（两者都是 OpenAI 兼容协议，`base_url` 即可切换）；后续换模型/加供应商不动业务代码 |
| D2 | 是否引入 LangGraph | **不引入** | 当前编排是固定 5 轮 function calling 循环 + 人工确认走 REST/画布，没有需要状态机、持久化检查点、动态分支的复杂 agent 流；LangGraph 会引入额外概念与依赖而无对应收益。若未来出现「多步自主 agent」（如自动巡检生成治理任务）再评估 |
| D3 | 自动补描述的落库路径 | **草稿位 → 人工确认 → annotation** | 新增 `description_draft` 表承载 AI 草稿（不动 `field.description` 原始导入值，符合「原始导入与人工见解分离」不变量）；用户在 UI 确认采纳后才写 `annotation`（追加式），拒绝则标记后不再重复生成 |
| D4 | MCP 暴露 | **做**，stdio 传输 | 把查询类工具暴露为 MCP server，Claude Desktop / Cursor 等外部 AI 可直接查血缘；REST 抽屉路线不变，两者共存 |
| D5 | embedding 供应商 | **OpenAI 与阿里云 DashScope 均支持**（经 D1 的 `OpenAIEmbeddings` base_url 切换） | 未配置 embedding 时语义层**优雅降级**为纯启发式，不阻塞其他功能【TBD-INFRA：需用户提供 embedding key，DeepSeek 不提供 embedding API】 |

## 四、技术设计

### 4.1 供应商矩阵（D1/D5）

| 供应商 | chat base_url | embedding base_url | 模型示例 |
|---|---|---|---|
| DeepSeek | `https://api.deepseek.com` | —（无 embedding API） | `deepseek-chat` |
| 阿里云 DashScope | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 同左 | `qwen-plus`；embedding：`text-embedding-v3` |
| OpenAI | `https://api.openai.com/v1` | 同左 | `gpt-4o-mini`；embedding：`text-embedding-3-small` |

`.env` 新增（均可空，空=功能降级）：

```
EMBEDDING_BASE_URL=          # 空则语义建议降级为纯启发式
EMBEDDING_API_KEY=
EMBEDDING_MODEL=             # 如 text-embedding-v3 / text-embedding-3-small
```

chat 侧沿用既有 `LLM_BASE_URL / LLM_API_KEY / LLM_MODEL`。

### 4.2 `ai/llm.py` 重写（D1）

- `get_chat_model()`：按 settings 构造 `ChatOpenAI(model, api_key, base_url, temperature=0, timeout=60)`（单例缓存）；
- `complete(messages, tools)`：**保留原签名**——内部把 OpenAI 格式消息/工具转为 LangChain 消息与 `bind_tools`，`invoke` 后转回 dict（`{choices:[{message:{content, tool_calls}}]}` 形态），既有 `chat.py` 编排与测试零改动；
- `stream_chat(messages, tools)`：`ChatOpenAI.stream` 产出 `AIMessageChunk`——chunk 含 `tool_call_chunks` 时不外发文本（本轮是工具轮），聚合为完整 `AIMessage` 返回；否则逐 token 外发；
- `get_embeddings()`：settings 配置了 `EMBEDDING_*` 时返回 `OpenAIEmbeddings`，否则 `None`（调用方降级）；
- `LLMNotConfigured / LLMError / endpoint_url` 语义不变（`endpoint_url` 保留兼容，LangChain 直接吃 base_url）。

### 4.3 SSE 流式编排（演进项 2）

`POST /ai/chat/stream`（viewer+）请求体同 `/ai/chat`，响应 `text/event-stream`：

```
event: token     data: {"delta": "…"}            # 最终回答逐 token
event: tool      data: {"tool":"trace_lineage","args":{…},"ok":true,"round":1}
event: suggest   data: {"count": 3, "candidates":[…]}   # suggest_lineage 落库后
event: drafts    data: {"items":[{id, dataset, field, draft}]}
event: done      data: {"highlights":[…], "graph":{…}|null}
event: error     data: {"detail": "…"}
```

编排循环与非流式同构（5 轮上限），差异仅在最终回答轮走 `stream_chat` 逐 token 外发；`tool/suggest/drafts` 事件在循环中即时发出。非流式 `/ai/chat` 保持不变（MCP/脚本消费）。

### 4.4 对话工具集（5 → 8 个）

| 工具 | 类型 | 说明 |
|---|---|---|
| `search_fields` / `get_field_details` / `trace_lineage` / `get_field_history` / `mark_highlight` | 既有 | 见 [03_后端开发文档](./03_后端开发文档.md) §8.2 |
| `suggest_lineage` | 写候选（`source='ai'` 落库，不变量#4 允许） | 参数 `{dataset, field}`；内部跑 `suggest.suggest_edges`（启发式 + 语义层）；返回候选清单，前端收 `suggest` 事件刷新画布 |
| `analyze_impact` | 只读 | 参数 `{dataset, field, hops?}`；聚合下游子图 + 各下游字段源文件核查状态 + 最近变更（change_log），返回结构化影响面 |
| `draft_descriptions` | 写草稿（`description_draft` 表，非业务数据） | 参数 `{dataset, fields?（≤10，缺省=该数据集全部缺描述字段）}`；逐字段调 chat 模型生成描述草稿（输入含类型/描述现状/上下游边/同名字段），落 pending 草稿 |

### 4.5 描述草稿流（D3）

```
模型调 draft_descriptions → description_draft(pending) → SSE drafts 事件
→ 抽屉渲染确认卡（采纳 / 拒绝）
→ accept: 写 annotation(target_kind='field', body=草稿, author=当前用户) + 置 accepted
→ reject: 置 rejected（不再重复生成同字段，除非字段内容变更）
```

DDL（`db.py init_db` 增量，SQLite）：

```sql
CREATE TABLE IF NOT EXISTS description_draft (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  dataset_id TEXT NOT NULL REFERENCES dataset(id),
  field_name TEXT NOT NULL REFERENCES field(dataset_id, name) ON DELETE CASCADE ON UPDATE CASCADE,
  draft TEXT NOT NULL,
  model TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','accepted','rejected')),
  created_at TEXT NOT NULL,
  decided_at TEXT,
  UNIQUE (dataset_id, field_name, status)
);
```

REST（均 editor+；viewer 只读 GET）：`GET /ai/description-drafts?dataset=`、`POST /ai/description-drafts/{id}/accept`、`POST /ai/description-drafts/{id}/reject`。

### 4.6 MCP server（D4）

- 传输：stdio；进程：`uv run python -m clew.ai.mcp_server`（与 API 同库同配置）；
- 暴露：`search_fields` / `get_field_details` / `trace_lineage` / `get_field_history` / `get_overview`（数据集清单 + 字段/边统计摘要）；
- **只读**：不暴露 suggest/mark_highlight/草稿写操作——外部 agent 不可触发写库（即便 `source='ai'`）；
- 接入示例（Claude Desktop / Cursor MCP 配置）：

```json
{ "mcpServers": { "lineagelite": {
    "command": "uv",
    "args": ["run", "--directory", "<仓库>/prototype/backend", "python", "-m", "lineagelite.ai.mcp_server"] } } }
```

## 五、明确不做

- **Text-to-SQL / 自然语言查数**：本产品无数据库连接，越界；
- **向量数据库**：embedding 召回用 SQLite 存向量 + 内存暴力检索足够；
- **AI 自治写业务数据**：任何写动作必须经人工确认（不变量#4）；MCP 仅暴露只读工具；
- **多租户记忆 / 跨用户 agent 记忆**：单机单人产品无需。
